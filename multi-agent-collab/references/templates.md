# 协作文档模板与填写要求

模板只给结构,尖括号内容必须换成从目标仓库核实的真实信息;查不到就写“待确认”,不要保留占位符也不要编造。默认中文,若项目或用户已有语言要求则沿用。

## 目录
- AGENTS.md
- CLAUDE.md
- docs/ai/PROJECT.md
- docs/ai/DECISIONS.md
- docs/ai/TASKS.md
- docs/ai/HANDOFF.md

---

## AGENTS.md

职责:所有 Agent 共用的稳定规则。不放会频繁变化的进度。

```markdown
# <项目名> · AI 协作规则

本文件供 Codex、Claude Code 和其他参与本工程的 Agent 共用。`CLAUDE.md` 是 Claude Code 的入口,项目事实和任务进度以 `docs/ai/` 与实际代码为准。

## 每次任务开始

1. 阅读 `docs/ai/TASKS.md` 和 `docs/ai/HANDOFF.md` 的最新记录;首次参与或架构变化时读 `PROJECT.md`;涉及历史选择时查 `DECISIONS.md`。
2. 执行 `git status --short --branch` 和 `git log -5 --oneline`<如 Git 根目录不在本目录,在此注明>。
3. 对照交接文档查看相关源码、差异和验证记录,确认上一个 Agent 的实际完成情况。`HANDOFF.md` 仅是线索,不是完成证明。
4. 在 `TASKS.md` 认领本次任务,写明 Agent 与状态;先看是否有人正在改相同文件,有冲突先向用户说明。
5. 开始编码前说明会影响产品行为、数据、安全或范围的假设;无法确定的重大选择先询问用户。

## 开发与协作

- 同一时间只允许一个 Agent 写入同一任务或文件;要并行,先改用独立 worktree 并约定合并方式。
- 保留他人及用户的未提交修改。禁止为整理工作树执行 `git reset --hard`、`git clean`、覆盖文件或批量暂存无关改动。
- 只修改本次任务需要的代码和文档;遵循现有结构、命名与风格。
- 已获用户确认且长期有效的决策,记录到 `docs/ai/DECISIONS.md`,注明日期、依据与影响;未确认的方案留在任务或交接文档。
- 完成修改后执行最小相关验证,记录命令或复现步骤及结果。未验证的行为标“待验证”;构建通过不等于功能通过。
- 用户在设备或界面上确认某项修复后,立即更新 `TASKS.md` 与 `HANDOFF.md`。

## 项目硬约束

<仅写用户明确说过的限制,每条带日期与原话依据。没有就删除本节。>

## 每次任务结束或中断前

1. 更新 `TASKS.md`:状态、已完成范围、验证证据、剩余工作;验收条件满足才标“已完成”。
2. 在 `HANDOFF.md` 顶部新增记录:日期、Agent、任务 ID、实际完成、变更文件、验证及结果、未解决问题、下一步。
3. 再检查 `git status --short --branch`,说明哪些原有未提交修改仍在工作树中,不把别人的修改写成自己的成果。
4. 被中断时仍记录可确认的进度,任务标“进行中”或“待验证”;禁止用推测补齐验证结果。

## 文档的职责

- `PROJECT.md`:稳定的项目介绍、架构、构建入口和关键路径。
- `DECISIONS.md`:已确认的重要决策及依据。
- `TASKS.md`:任务状态、负责人、验收条件和证据。
- `HANDOFF.md`:最近一次工作的事实快照与接手建议;优先看最新记录,再回到代码核实。
```

## docs/ai/PROJECT.md

职责:接手者 5 分钟内能弄清项目是什么、怎么构建、关键代码在哪。只写已核实的稳定信息,进度放 TASKS。

建议栏目:
1. **产品与技术**:用途、语言/框架、依赖管理方式、构建入口。
2. **环境与 Git**:项目绝对路径、Git 根目录(若与项目目录不同要写明)、分支约定。
3. **目录与关键代码**:表格,`路径 | 作用`,只列已读过确认的。
4. **构建与检查命令**:命令、执行目录、来源(哪个脚本/文件);区分“脚本存在”和“已运行成功”,没有测试脚本就如实写没有。
5. **专项资料入口**:项目已有的流程图、分析、设计稿等,给相对链接。

页首写“更新:YYYY-MM-DD”。

## docs/ai/DECISIONS.md

职责:只记录有用户明确依据、或仓库已实现且必须遵守的决策。

```markdown
# <项目名> · 已确认决策

只记录有用户明确依据的决策。新方案未获确认时先写入任务或交接记录。

## YYYY-MM-DD · <决策标题>

- **依据**:<用户原话,或指向确认它的会话/文件>
- **内容**:<决定了什么>
- **执行边界**:<做什么、不做什么>
- **验收**:<怎么确认遵守了>
```

最新的放最上面。历史理由不明的,写“理由待确认”,不要补写。

## docs/ai/TASKS.md

```markdown
# <项目名> · 任务清单

更新:YYYY-MM-DD。状态只使用:`待办`、`进行中`、`待验证`、`已完成`、`受阻`。负责人写 Agent 名称或“未认领”;完成需留下可复查证据。

| ID | 任务与验收条件 | 状态 | 负责人 | 证据 / 下一步 |
| --- | --- | --- | --- | --- |
| AI-001 | 建立多 Agent 协作文档;验证文件存在、链接与 Git 差异 | <状态> | <Agent> | <日期与检查结果> |

## 维护约定

- 开始任务时认领对应行并写清范围;新任务分配新 ID(按类别前缀加序号)。大任务拆成可验收的小项。
- “进行中”表示正在改;“待验证”表示已有结果但验收条件尚未证实;“受阻”需写明阻碍。
- 只有达到验收条件、且验证结果可复查时才标“已完成”。
- 如 Git 状态与本表不符,以实际代码和验证证据为准,先修正本表再继续。
```

## docs/ai/HANDOFF.md

职责:最近几次工作的事实快照。最新记录在顶部,保留近期记录即可,旧的可以裁掉。

```markdown
# <项目名> · 最近交接

每次结束或中断任务,把最新记录放在顶部。接手时先核对 Git、相关源码和验证证据,再更新 `TASKS.md`。

## YYYY-MM-DD · <Agent> · <任务 ID>

### 实际完成
- <做了什么;根因若是推断,写明“推断,未验证”>

### 变更文件
- `<路径>`:<改了什么>

### 验证及结果
- <命令或复现步骤> → <结果>。未做的验证明确写“未做”。

### 未解决问题与下一步
1. <接手者最该先做的事>

### 工作树状态
- <仍在工作树里的原有未提交改动,说明不是本次产物>
```

写作要求:只写能确认的事实;推断、猜测单独标出;不记录密钥、令牌、账号密码。
