# 多 Agent 协作方案(通用)

让 Codex、Claude Code 等多个 Agent 在**同一个工作树**里轮流接力,每个 Agent 不靠记忆,靠仓库里的文件和真实代码接手。这套做法来自 LiftBlue 项目的实践,与技术栈无关,所以文档里的项目事实一律从目标仓库现场核对,不照搬任何旧项目。

方案的核心只有一条:**交接文档是线索,代码和验证证据才是事实**。下一个 Agent 读 HANDOFF 之后必须回到 Git 和源码核实,因此文档里写“完成”不能当成完成的证据。

```text
<项目根目录>/
├── AGENTS.md          # 所有 Agent 共用的规则
├── CLAUDE.md          # Claude Code 入口,默认只写 @AGENTS.md
└── docs/ai/
    ├── PROJECT.md     # 稳定的项目介绍、架构、构建入口、关键路径
    ├── DECISIONS.md   # 用户已确认的重要决策(带日期和依据)
    ├── TASKS.md       # 任务状态表(认领、验收条件、证据)
    └── HANDOFF.md     # 最近几次交接,最新的在顶部
```

## 先判断模式

| 情形 | 模式 |
| --- | --- |
| 用户要求初始化 / 补齐协作文档,或项目里还没有这套文件 | **A. 初始化** |
| 项目已有 `docs/ai/`,正在开始、结束或中断一项任务 | **B. 日常协议** |

两种模式可以连着用:先初始化,再按 B 的流程认领第一项任务(初始化本身也是一项任务)。

---

## 模式 A:初始化

默认直接执行,而不是只给方案。只改协作文档和必要的忽略配置,不顺手做业务开发、装依赖、构建、提交或推送。

### 1. 定位项目与 Git 边界
- 目标优先取用户明确给出的目录,否则取当前工作目录。工作目录是一堆项目的集合、没有唯一目标时,先问是哪一个,不要默认全部初始化。
- 工程目录不一定是 Git 根目录(LiftBlue 的 Git 根在工程目录的上一级)。用 `git rev-parse --show-toplevel` 确认真实根目录,后面的忽略规则要按这个根目录写路径。没有 Git 仓库时不自动 `git init`,把能做的文档做完并报告这一限制。
- 记录写入前的基线:`git status --short --branch`、`git log -5 --oneline`。里面已有的未提交改动属于别人,保持原样,暂存区不动。
- 读路径上已有的 `AGENTS.md`、`CLAUDE.md`、子目录规则和已有 `docs/ai/`,先理解再写,别覆盖。

### 2. 核对项目事实
只读填写文档所需的少量文件:构建/依赖配置、入口、目录结构、README、已有脚本。每一条写进 PROJECT 的事实都要有来源;查不到的写“待确认”,不要用常见做法补空。区分“脚本存在”和“已运行成功”。

### 3. 生成或合并
文件内容、栏目和模板见 [references/templates.md](references/templates.md),生成前先读。要点:
- 已有文件**增量合并**,保留有效的规则、决定和未完成任务;重复调用只补缺口、刷新有证据的过时信息,不重复追加。
- 已有别的状态入口(如 `STATE.md`、`PLAN.md`)时,保留原文并说明各类信息以哪个为准,避免两套互不同步的状态。
- `CLAUDE.md` 不存在就创建,内容为 `@AGENTS.md`;已存在就保留原文,只检查导入链,补必要引用,避免循环。
- AGENTS 里的“项目硬约束”只写用户**亲口说过**的限制;没有就删掉这一节。不要替用户发明保护区。
- TASKS 里加一条“初始化协作文档”任务,HANDOFF 写首条记录。初始化完成不等于业务完成,不要这样表述。

### 4. Git 忽略(默认本机忽略)
协作文档里常有本机路径、测试账号、未确认的推断,所以默认只放在本机,不进仓库。在**真实 Git 根目录**的 `.gitignore` 里,按相对根目录的路径增量添加锚定规则,已有生效规则不重复加:

```gitignore
/<相对根目录的前缀>/AGENTS.md
/<相对根目录的前缀>/CLAUDE.md
/<相对根目录的前缀>/docs/ai/
```

- 只忽略这些协作文件,不要用 `**/docs` 之类宽泛规则,否则会把项目里真正需要提交的文档一并藏起来。
- 忽略不会取消已跟踪文件。遇到已跟踪的协作文档,保留其跟踪状态并报告,不执行 `git rm --cached`、强制添加、stash 或 reset。
- 用户明确说要共享/提交这些文档时,跳过忽略,按用户要求处理。
- 在 HANDOFF 里注明:本机文件不会随 clone 或新 worktree 自动带走,换机器或建 worktree 前要手动迁移。

### 5. 验收与交付
- 检查五个文件齐备、引用路径存在、CLAUDE 入口无重复或循环、旧规则/任务/决定都保留。
- 用 `git check-ignore -v` 验证忽略生效,用 `git ls-files` 区分已跟踪的例外;对本次改动的已跟踪文件跑 `git diff --check`。
- 对照基线,确认无关的业务文件、锁文件、暂存区没有变化。
- 简要汇报:生成/合并了哪些文件、Git 边界、忽略结果、已检查和未检查的项、下次接手从哪里开始。没做的验证(例如新会话加载、构建)如实说没做。

## 模式 B:日常协议

这是所有 Agent 在这类项目里的接力规矩。AGENTS.md 里已写同样内容时以 AGENTS.md 为准,本节用于没有读到它时兜底。

### 任务开始
1. 读 `TASKS.md` 和 `HANDOFF.md` 最新记录;第一次参与或架构变了才读 `PROJECT.md`;涉及历史选择时再查 `DECISIONS.md`。上下文还有效就别重读全套。
2. 运行 `git status --short --branch` 和 `git log -5 --oneline`,对照 HANDOFF 看上一位 Agent 实际做到了哪一步。
3. 在 TASKS 认领本次任务(写上 Agent 和状态)。先看有没有别人正在改同一批文件,有冲突先跟用户说。
4. 会影响产品行为、设备、数据、安全或范围的假设,动手前说出来;靠代码和需求定不下来的重大选择,先问用户。

### 工作中
- 同一时间只有一个 Agent 往同一个工作树写入。要并行,先开独立 worktree 并约定怎么合并。
- 保留他人和用户的未提交改动;不用 `git reset --hard`、`git clean`、覆盖文件或批量暂存来“整理”工作树。
- 只改本次任务要改的,沿用现有代码风格和结构。
- 写进 DECISIONS 的必须是用户明确确认过的决定,带日期和依据;没确认的方案留在 TASKS 或 HANDOFF。
- 做最小的相关验证,记下命令或复现步骤和结果。构建通过、截图不等于功能通过;没验证的标“待验证”,涉及真机、设备、线上环境的更不要用模拟结果代替。

### 用户确认一项修复后
用户在设备或界面上确认修复有效时(比如说“已解决,更新交接文档”),就在这一刻更新 TASKS 和 HANDOFF,别攒到最后。这样中途换人或被打断,文档仍是最新的。

### 任务结束或中断
1. 更新 `TASKS.md`:状态、已完成范围、验证证据、剩余工作。状态只用 `待办 / 进行中 / 待验证 / 已完成 / 受阻`,验收条件满足且证据可复查才标“已完成”。
2. 在 `HANDOFF.md` **顶部**加一条记录:日期、Agent、任务 ID、实际完成、变更文件、验证及结果、未解决问题、下一步。
3. 再看一遍 `git status`,说明哪些原有未提交改动仍在工作树里,不要把别人的改动写成自己的成果。
4. 被打断也要记录能确认的进度,任务标“进行中”或“待验证”;不要用推测补齐没做过的验证。

---

## 与长期记忆的关系
如果用户有自己的长期记忆库(全局 CLAUDE.md 里会写入口),协作文档只管**这个项目的接力**,不替代它。任务收尾时,跨项目的偏好或决策按记忆库的协议另行处理,项目里的 DECISIONS 不必重复抄一份。

## 不要做的事
- 不把某个旧项目的任务、决策、路径、命令、颜色规则之类搬进新项目。
- 不在文档里写密钥、令牌、账号密码或完整敏感日志;遇到测试账号之类,只写“存在且不提交”。
- 不把工具特有的权限、MCP、技能安装情况写成两个 Agent 天然共享。
- 不为了填满模板而编造信息。
